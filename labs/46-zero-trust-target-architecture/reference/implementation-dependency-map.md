
# Implementation Dependency Map

The dependency model is phase-gated, profile-driven, and package-specific. Phase exit criteria are prerequisites for the next phase; architecture documentation never satisfies a runtime gate.

`ZT-NET-001` is implemented, runtime validated, and accepted for one bounded directional inter-zone ACL. Its fixed 39-check validator, allow and explicit-deny probes, restricted endpoint, stopped-to-running persistence, denial event, and rollback evidence are accepted without promoting broader segmentation, encryption, SDN, resilience, production scope, or maturity.

`ZT-ID-001` is an implemented and runtime-validated Phase 1 identity package for one bounded non-production validator endpoint. Its synthetic policy suite remains locally validated, while the accepted runtime scope covers a dedicated validator account/group, forced command, SSH restrictions, exact sudo allowlist, recovery, and deterministic allow/deny evidence. It does not establish centralized identity, MFA, OIDC, application RBAC, production validation, or maturity. `ZT-DEV-001` is implemented and partially runtime validated for six classified aliases and one mandatory live VM; broad endpoint management, EDR/XDR, patch automation, and device authorization remain absent. `ZT-APP-001` is implemented and partially runtime validated for two applications, four workloads, a partial direct-image SBOM, and one unchanged non-critical Alloy pilot; immutable provenance, signing, transitive vulnerability coverage, and broad deployment enforcement remain absent. `ZT-DATA-001` is implemented and partially runtime validated for seven metadata-only assets, manual labels, detection-only DLP, and one isolated synthetic restore; enterprise governance, dynamic access, platform encryption, live backup/restore, blocking DLP, and continuous analysis remain absent. `ZT-SYS-001` is implemented and partially runtime validated for seven bounded systems, five safe matched configuration authorities, and existing fixed read-only runtime validators; OpenStack remains `CURRENT_DEGRADED` at 46/0/4, and complete PAM, credential lifecycle, continuous FIM, broad hardening, automatic recovery, and full system restore remain absent. `ZT-AUTO-001` is implemented and partially runtime validated for fixed R0-R3 handlers, default-deny policy, deterministic plans, proposal-only governance, and one partial cross-domain read-only execution; arbitrary execution, R4-R8 mutation, external notification, autonomous response, repeatability, scheduling, SOAR, and maturity remain absent. `ZT-ID-002` remains a separate later Phase 2 candidate. `ZT-VIS-001` is runtime validated and accepted only for four attributed sanitized summary sources and one single-node local Grafana/Loki/Alloy stack. Its service, loopback, retention, ingestion, permissions, freshness, restart, and rollback boundaries passed; external NTP synchronization, continuous observation, broad source onboarding, and enterprise central visibility remain open. `ZT-VIS-002` is partially implemented, partially runtime validated, and partially accepted for one bounded private non-production OpenStack monitoring VM and does not inherit ZT-VIS-001 authority. Identity-based Grafana access remains a Phase 2 design use case. IaC, Configuration as Code, and Policy as Code convergence waits for cross-domain signal and enforcement validation.

`implementation-dependency-map.yaml` is the machine-readable authority. It records Phase 1 as `PARTIAL` / `PARTIALLY_VALIDATED` / `COMPLETED_WITH_GAPS` at the historical bounded `ZT-RV-001` EC4 boundary, records P1-ACC-001 as `ACCEPTED_WITH_GAPS` under `P1-RV-FRESHNESS-001`, records Phase 2 as `IN_PROGRESS_PARTIAL_RUNTIME`, records `ZT-SCH-001` as installed, disabled, and deferred to the final Phase 5 gate with zero accepted scheduled dates, and records later packages only as design, not-started, unassessed, or roadmap-only work.

ZT-VIS-002 records the separately bounded Cinder LVM prerequisite, four-resource
private deployment, five fixed runtime components, mTLS enforcement, sanitized
ingestion, restart persistence, package-only rollback, preserved-data recovery,
cleanup, and evidence integrity. The accepted one-time campaign supports only
partial runtime status at EC3. Alert-rule and notification delivery,
elapsed-retention behavior, and full Cinder snapshot rebuild/reattachment
restore remain open before P2-VIS-001 completion.
